# Sprint 17 — End-to-End MLOps Pipeline

**A reproducible machine learning workflow for the UCI Adult Income classification dataset.** The project covers data versioning, exploratory analysis, leakage-aware preprocessing, configurable model training, MLflow experiment tracking, explicit model promotion, data drift monitoring, robustness evaluation, automated testing, and GitHub Actions orchestration.

The emphasis is on **how the complete model lifecycle is implemented and why each design choice was made**, rather than treating an individual training run as the project itself. The EDA is retained here because its findings directly motivate the preprocessing and evaluation strategy. Execution-specific results belong in the artifacts generated by the pipeline.

## Quick start

From the repository root, after installing dependencies (Section 3):

```bash
# Reproducibility-oriented quick check; includes DVC restoration.
python -m scripts.run_pipeline --quick --pull-dvc

# Full training sweep, scoped MLflow comparison, and all downstream stages.
python -m scripts.run_pipeline --full --pull-dvc
```

Both modes run tests, preprocessing, training, drift generation, drift monitoring, and robustness evaluation against the **existing promoted reference model**. Full mode additionally compares models trained during the current execution and exports `reports/mlflow_comparison.csv`. Quick mode is a smoke test and does not create a promotable candidate. The candidate counts depend on `configs/config.yml` (currently 12 quick candidates and 54 full candidates).

**The pipeline never promotes a model automatically.** Promotion is a separate, explicitly authorized action. Synthetic severe drift intentionally triggers a CRITICAL alert; the orchestrator treats monitoring exit code `1` as an expected alert, not a pipeline execution failure.

Responsibilities are deliberately separate:

- **Git / GitHub** versions source code, YAML configuration, tests, documentation, GitHub Actions workflows, and DVC pointer files.
- **DVC + S3** provides content-addressed storage for the raw Adult data and the approved reference model; **DVC is not the pipeline orchestrator** in this project.
- **`src/data/preprocess.py`** defines input validation, duplicate-aware partitioning, feature engineering, and the three preprocessing variants.
- **`configs/config.yml`** defines training variants, model families, fixed/swept hyperparameters, seed, paths, and MLflow settings. It is distinct from the Python preprocessing configuration.
- **`src/models/train.py`** builds and evaluates candidates, optimizes classification thresholds on validation data, logs MLflow runs, and saves isolated artifacts.
- **`scripts/compare_experiments.py`** compares completed MLflow candidates with deterministic ranking and optional execution-ID filtering.
- **`scripts/run_pipeline.py`** owns stage ordering and runs **the full-mode MLflow comparison exactly once**. The manual GitHub Actions workflow does **not** duplicate that operation.
- **`src/data/monitoring.py`** compares feature distributions with Evidently and records both aggregate drift and individual drifted feature names.
- **`src/models/robustness.py`** evaluates the existing promoted reference model under labeled synthetic drift scenarios.
- **`src/models/promote.py`** validates and, only on explicit confirmation, installs a new reference model.

```bash
python -m pytest tests/ -q

```

Some tests intentionally load the real DVC dataset and will fail when those files are absent. `joblib` models use pickle-compatible serialization and must only be loaded from trusted sources.
## 4. Dataset and exploratory analysis

The project includes a comprehensive Exploratory Data Analysis (EDA) covering data quality, feature distributions, statistical associations, predictor relationships, feature redundancy, and potential feature interactions.

**Complete analysis:** [Exploratory Data Analysis Notebook](notebooks/01_eda.ipynb)

The notebook contains the Python code, statistical tests, visualizations, interpretations, and preprocessing recommendations supporting the findings summarized below.

### 4.1 Dataset Source and Structure

The project uses the [UCI Adult (Census Income) dataset](https://archive.ics.uci.edu/dataset/2/adult), combining:

| Source | Observations |
|---|---:|
| `adult.data` | 32,561 |
| `adult.test` | 16,281 |
| **Combined dataset** | **48,842** |

The dataset contains **14 predictors** (6 numerical and 8 categorical) and one binary target, `income`.

The first line of `adult.test` is skipped, trailing periods are removed from its income labels, and `?` values are interpreted as missing.

The original UCI train/test division is not reused. The project creates its own train, validation, and held-out test partitions.

The classification target is:

- `<=50K`: Annual income of $50,000 or less.
- `>50K`: Annual income exceeding $50,000 (positive class).

### 4.2 Data Quality Assessment

#### Duplicate records

The EDA identified:

- **52 duplicate occurrences** (0.11% of the dataset).
- **101 observations** belonging to 49 distinct duplicate groups.
- Most duplicate groups contain two observations; three groups contain three.

Because the dataset does not provide unique individual identifiers, identical records cannot automatically be classified as erroneous duplicates.

**Decision:** Retain all observations. The implemented preprocessing pipeline uses duplicate-aware partitioning logic to reduce the risk of identical observations appearing across different partitions.

#### Missing values

| Feature | Missing count | Missing percentage |
|---|---:|---:|
| `workclass` | 2,799 | 5.73% |
| `occupation` | 2,809 | 5.75% |
| `native-country` | 857 | 1.75% |

Overall, **3,620 observations (7.41%)** contain at least one missing value.

Further investigation identified two important patterns:

1. All 2,799 observations with missing `workclass` also have missing `occupation`.
2. Approximately 9.5% of observations with missing employment information belong to the high-income class, compared with approximately 24.8% among observations with recorded employment information.

These findings suggest that missing employment information may contain predictive information.

**Decision:** Preserve missing observations and represent missing categorical values using a dedicated `Unknown` category rather than deleting rows or replacing missing values with the most frequent category.

### 4.3 Feature Distributions and Class Imbalance

#### Numerical distributions

The six numerical predictors exhibit different distributional characteristics:

- `age`: Moderately right-skewed, with a mean of 38.64 years.
- `fnlwgt`: Right-skewed, reflecting substantial variation in census sampling weights.
- `education-num`: Ordinal educational attainment, with a median of 10.
- `hours-per-week`: Concentrated around 40 hours, with a maximum of 99.
- `capital-gain`: Extremely right-skewed and predominantly zero.
- `capital-loss`: Strongly right-skewed and predominantly zero.

The financial features require special treatment because conventional scaling alone does not address their extreme zero inflation and skewness.

#### Categorical distributions

Categorical predictors exhibit substantial frequency imbalances and varying cardinality.

`native-country` has the highest cardinality, with **41 categories**, heavily dominated by `United-States`.

Other features, including `occupation` and `workclass`, contain rare categories that may produce sparse or unstable encoded representations.

These findings support categorical encoding with appropriate handling of infrequent and previously unseen categories.

#### Target distribution

| Income class | Observations | Percentage |
|---|---:|---:|
| `<=50K` | 37,155 | 76.1% |
| `>50K` | 11,687 | 23.9% |

The majority-to-minority ratio is approximately **3.18:1**.

A classifier that always predicts `<=50K` would achieve approximately 76.1% accuracy while failing to identify any positive-class observations.

**Modeling implications:**

- Use stratified partitioning to preserve class proportions.
- Prioritize positive-class F1 for model selection.
- Report precision, recall, ROC-AUC, and PR-AUC as complementary evaluation metrics.
- Avoid relying on accuracy alone.

### 4.4 Statistical Associations with Income

The EDA used statistical tests and effect-size measures to quantify relationships between individual predictors and the binary income target.

These are observational associations, not causal effects or direct measures of model feature importance.

#### Numerical predictors

Point-biserial correlation and Mann–Whitney U tests were applied to the six numerical predictors.

| Feature | Point-biserial r | Rank-biserial |
|---|---:|---:|
| `education-num` | 0.3326 | 0.4325 |
| `age` | 0.2304 | 0.3645 |
| `hours-per-week` | 0.2277 | 0.3437 |
| `capital-gain` | 0.2230 | 0.1794 |
| `capital-loss` | 0.1476 | 0.0684 |
| `fnlwgt` | -0.0063 | -0.0080 |

Five numerical predictors showed statistically significant associations with income (p < 0.0001). `fnlwgt` showed negligible marginal association and was not statistically significant.

**Key interpretation:** Educational attainment exhibits the strongest numerical association with income, followed by age and working hours. Financial variables also contain useful statistical signals despite their highly skewed distributions.

A weak marginal association does not necessarily imply that a feature lacks multivariate predictive value.

#### Categorical predictors

Chi-square tests of independence and Cramér's V were used to evaluate categorical associations.

| Feature | Cramér's V |
|---|---:|
| `relationship` | 0.4545 |
| `marital-status` | 0.4483 |
| `education` | 0.3659 |
| `occupation` | 0.3500 |
| `sex` | 0.2146 |
| `workclass` | 0.1816 |
| `race` | 0.0999 |
| `native-country` | 0.0962 |

All eight categorical predictors showed statistically significant associations with income (p < 0.05), although their effect sizes varied.

Household relationships, marital status, education, and occupation exhibited the strongest categorical associations.

**Important distinction:** Statistical significance does not establish predictive usefulness, independence, or causality. Final feature and model decisions must be supported by validation performance.

### 4.5 Predictor Relationships, Redundancy, and Interactions

#### Numerical correlations

Pearson and Spearman correlation matrices showed weak pairwise correlations among numerical predictors.

- Maximum absolute Pearson correlation: **0.144**.
- Maximum absolute Spearman correlation: **0.164**.

The strongest numerical relationship was between `education-num` and `hours-per-week`, but its magnitude remained weak.

No numerical feature was excluded solely because of pairwise correlation.

#### Categorical relationships

Several categorical predictors exhibited moderate to strong associations with one another.

| Feature pair | Cramér's V |
|---|---:|
| `relationship` × `sex` | 0.65 |
| `marital-status` × `relationship` | 0.49 |
| `marital-status` × `sex` | 0.46 |
| `occupation` × `sex` | 0.42 |
| `occupation` × `workclass` | 0.40 |
| `race` × `native-country` | 0.40 |

These relationships indicate overlapping information, particularly among household and employment characteristics.

However, statistical association does not imply complete redundancy, and the features were retained for initial modeling.

#### Education redundancy

The notebook confirmed a **one-to-one mapping between all 16 `education` categories and their corresponding `education-num` values**.

Both variables therefore encode the same educational attainment information.

**Implemented decision:** Retain `education-num` and exclude the textual `education` representation from the preprocessing feature set.

#### Feature interaction investigation

Three combinations were explored:

| Interaction | Main observation | Small subgroups (n < 30) |
|---|---|---:|
| Education × Age | Higher education is associated with higher income rates, particularly at ages 31–60 | 4 / 64 |
| Occupation × Working Hours | Income rates vary across occupations and working-hour groups | 6 / 60 |
| Marital Status × Education | Income rates differ across combinations of marital status and educational attainment | 34 / 104 |

The subgroup differences motivated investigation of engineered interaction features.

However, these descriptive patterns do not establish statistically significant interactions or guarantee improved predictive performance.

**Implemented decision:** Evaluate interaction features through a separate `interactions` preprocessing variant and compare performance against the baseline using validation data.

### 4.6 Capital Gain and Loss Investigation

The financial variables received additional analysis because of their extreme skewness and unusually high proportions of zero values.

#### Zero inflation

| Statistic | `capital-gain` | `capital-loss` |
|---|---:|---:|
| Zero observations | 44,807 | 46,560 |
| Zero percentage | 91.74% | 95.33% |
| Positive observations | 4,035 | 2,282 |
| Unique positive values | 122 | 98 |

The zero values represent reported absence of capital gains or losses and should not be treated as missing data.

#### Association with income

| Financial condition | High-income rate |
|---|---:|
| Positive capital gain | 61.73% |
| Zero capital gain | 20.52% |
| Positive capital loss | 50.13% |
| Zero capital loss | 22.64% |

Positive capital gains and losses are associated with substantially higher proportions of high-income observations.

The notebook also established that **no observation contains both a positive capital gain and a positive capital loss**.

#### Maximum capital gain

The maximum recorded capital gain is **$99,999**, appearing in 244 observations (0.50% of the dataset).

All 244 observations belong to the `>50K` income class.

This concentration may reflect top-coding or a special reporting convention, but its cause was not independently verified. The value was not automatically classified as erroneous or removed.

**Implemented feature engineering:**

- Preserve the zero/nonzero distinction using binary indicators.
- Apply `log1p` transformations to reduce the scale of positive financial values.
- Retain the original capital variables alongside their transformations in the `robust` variant.
- Compare alternative representations through validation rather than selecting transformations solely from exploratory associations.

### 4.7 EDA Conclusions and Preprocessing Decisions

The exploratory analysis directly informed the project's preprocessing and evaluation design.

| EDA finding | Implemented decision |
|---|---|
| Missing employment information is associated with income | Preserve rows and impute missing categorical values as `Unknown` |
| Identical records may represent different individuals | Retain duplicates and use duplicate-aware partitioning |
| Target distribution is imbalanced (3.18:1) | Stratified partitions and positive-class F1 selection |
| Financial variables are highly zero-inflated | `log1p` transformations and binary positive-value indicators |
| Some categorical predictors have rare levels | One-hot encoding with infrequent/unseen category handling |
| `education` and `education-num` are redundant | Retain `education-num` and exclude textual `education` |
| Numerical predictors have weak pairwise correlations | Avoid correlation-based feature removal |
| Subgroup analysis suggests potential interactions | Evaluate a separate `interactions` variant |
| Numerical distributions contain skewness and extreme values | Compare standard and robust scaling strategies |

The original notebook proposed several alternative preprocessing and evaluation approaches. The final implementation uses three explicit preprocessing variants (`baseline`, `robust`, and `interactions`) and dedicated training, validation, and held-out test partitions.

All learned preprocessing parameters are fitted on training data only. Validation data is used for candidate selection and decision-threshold optimization, while held-out test data is reserved for evaluating selected configurations.

**Overall conclusion:** The EDA identified meaningful associations between income and education, age, employment characteristics, household relationships, and financial variables. It also revealed missing-data patterns, class imbalance, feature redundancy, rare categories, and opportunities for feature engineering.

These findings informed the implemented pipeline, but predictive performance and feature usefulness are ultimately determined through model validation rather than exploratory statistics alone.

The dataset contains sensitive demographic attributes and historical socioeconomic patterns. Statistical associations are not causal conclusions, and the model is not suitable for consequential individual decisions without additional fairness, validity, and governance assessments.
## 5. Data preprocessing

Preprocessing implements the decisions established in the EDA (Section 4): preserve missing and duplicate observations, keep `education-num` rather than the redundant textual `education` predictor, use suitable representations of capital gains/losses, manage rare categories, and test feature interactions as a separate configuration.

### 5.1 Running and configuring preprocessing

```bash
# Generate all variants.
python -m scripts.run_preprocessing

# Generate one variant.
python -m scripts.run_preprocessing --config baseline
python -m scripts.run_preprocessing --config robust
python -m scripts.run_preprocessing --config interactions
```

`PreprocessingConfig` in `src/data/preprocess.py` controls preprocessing options. This Python configuration is **not** the model-training YAML in `configs/config.yml`. The runner loads and combines the two Adult files, validates them, creates consistent partitions, fits transformations on the training set, applies them to the validation and test sets, and saves processed CSV files plus fitted transformers.

### 5.2 Input cleaning and duplicate-aware splitting

- Read `adult.data` and `adult.test`, skipping the introductory line in `adult.test`.
- Normalize target labels by removing trailing periods and interpreting `?` as missing.
- Encode income `<=50K` as `0` and `>50K` as `1`.
- **Keep duplicate observations** because equal records do not establish that the underlying individuals are identical.
- Build groups from **complete raw predictor vectors** (not target labels); keep identical predictor vectors together across partitions, including groups with differing targets.
- Approximate stratification at group level and split into approximately **64% training, 16% validation, and 20% test**.

The resulting partitions are shared across all variants. Group-aware splitting reduces leakage from duplicate predictor records. It may produce small deviations from the nominal split proportions.

| Partition | Role |
|---|---|
| Training | Fit all learned transformations and classifiers |
| Validation | Rank candidates and tune decision thresholds |
| Held-out test | Evaluate selected variant winners, not choose them |

### 5.3 Feature transformations

| Decision | Implementation | EDA rationale |
|---|---|---|
| Missing categorical values | Replace with `Unknown` | Missingness may carry signal; avoid deleting observations |
| Missing numerical values | Median imputation | Stable treatment of missing numeric values |
| Rare/unseen categories | `OneHotEncoder(handle_unknown="infrequent_if_exist")` | Categorical sparsity, especially in country and occupation |
| Educational attainment | Keep `education-num`, drop textual `education` | One-to-one correspondence between the two fields |
| Financial amounts | `log1p` features and zero/nonzero indicators | Severe skew and zero inflation |
| Scaling | Standard or robust scaling by variant | Explore sensitivity to outliers |
| Interactions | Age × education; occupation-specific working hours | Investigate subgroup patterns rather than assume their value |

The logarithmic feature representation is `log1p(x) = ln(1 + x)`. Zero amounts remain zero after transformation; binary indicators separately record whether amounts are positive. The `robust` variant retains original financial values alongside transformed values.

The project uses scikit-learn `Pipeline`, `ColumnTransformer`, `SimpleImputer`, `StandardScaler`/`RobustScaler`, and `OneHotEncoder`, alongside custom `AdultFeatureEngineer` and `OccupationHoursTransformer` components. Learned parameters and encoder vocabularies are fitted **only on training data**.

### 5.4 Preprocessing variants

| Variant | Scaling | Financial representation | Interactions | Default processed features |
|---|---|---|---|---:|
| `baseline` | StandardScaler | `log1p` + positive indicators | None | 53 |
| `robust` | RobustScaler | Original + `log1p` + indicators | None | 55 |
| `interactions` | StandardScaler | `log1p` + indicators | Age/education and occupation/hours | 68 |

The numbers describe the configured pipeline's output dimensions and may change if encoder settings or features are revised. Variant comparison is based on downstream validation metrics, not EDA intuition alone.

### 5.5 Generated artifacts

Each `data/processed/<variant>/` folder contains `X_train.csv`, `y_train.csv`, `X_val.csv`, `y_val.csv`, `X_test.csv`, `y_test.csv`, and `preprocessing_config.json`. The fitted transformers are stored at `models/preprocessors/<variant>.joblib`.

These artifacts are **generated**, not automatically committed to Git or tracked by DVC. Saved transformations are reused during training; the training module does not recreate the train/validation/test split.

## 6. Training and MLflow

`src/models/train.py` trains candidates from the saved preprocessing variants, ranks them using **validation positive-class F1**, logs experiments to MLflow, and saves artifacts under isolated execution directories. The objective is a reproducible model-development process, not an exhaustive search for globally optimal predictive performance.

### 6.1 YAML-controlled experiments

**Source of truth:** [`configs/config.yml`](configs/config.yml). The configuration defines the random seed, selected variants, output and tracking paths, MLflow experiment name, and each model family's fixed settings and parameter grid. The trainer validates the schema; currently it supports four specified model families and `selection_metric: val_f1`.

| Model family | Purpose | Default grid / variant |
|---|---|---|
| Logistic Regression | Interpretable linear classification baseline | `C`: 0.1, 1.0, 10.0 × `class_weight`: null, balanced = 6 |
| Random Forest | Nonlinear bagged decision trees | `max_depth`: null, 15 × `min_samples_leaf`: 1, 5 = 4 |
| HistGradientBoosting | Histogram-based gradient-boosted trees | `learning_rate`: 0.05, 0.1 × `max_leaf_nodes`: 15, 31 = 4 |
| Extra Trees | Highly randomized tree ensemble | `max_depth`: null, 15 × `min_samples_leaf`: 1, 5 = 4 |
| **Total** | | **18 configurations per variant** |

The default fixed settings include `max_iter: 5000`, `solver: lbfgs`, and `tol: 0.0001` for Logistic Regression; `n_estimators: 150` and `n_jobs: -1` for Random Forest and Extra Trees; and `max_iter: 150` for HistGradientBoosting. The seed defaults to `42`. Logistic Regression also uses an additional candidate-level `StandardScaler` fitted on the training matrix.

The trainer enumerates the **Cartesian product** of configured hyperparameters; it does not call `GridSearchCV`, `RandomizedSearchCV`, or Optuna. These values are **defaults**, not fixed requirements: changing the YAML changes the number and identity of candidates.

### 6.2 Quick versus full training

```bash
# Smoke check: first grid combination from each family and variant.
python -m src.models.train --quick

# Full YAML-defined Cartesian-product sweep.
python -m src.models.train

# Training can also be given an explicit complete YAML file.
python -m src.models.train --config configs/config.yml
```

- **Quick:** One configuration per model family per variant (12 with the default YAML). Checks training, validation, threshold calculation, and MLflow integration. It does not evaluate the held-out test set or package a promotable candidate; failure of a candidate fails the smoke check.
- **Full:** All configured combinations (54 with the default YAML). Selects a winner for each preprocessing variant using validation F1, evaluates those variant winners on the held-out test set, and packages the validation-preferred candidate as **unpromoted**.

The shared orchestrator's `--full` mode additionally runs `scripts.compare_experiments` for the **current** training execution. The direct `src.models.train` command does not run that separate comparison. The shared orchestrator uses the default `configs/config.yml` and does not forward a custom `--config` argument.

### 6.3 Selection, threshold optimization, and leakage safeguards

For each candidate, the training process:

1. Fits the classifier on the training partition.
2. Calculates positive-class probabilities on validation data.
3. Chooses the decision threshold that maximizes positive-class **validation F1**, using `precision_recall_curve()`.
4. Records F1, precision, recall, accuracy, ROC-AUC, average precision (logged as `pr_auc`), and a confusion matrix.
5. Ranks candidates by validation F1; uses validation average precision and then validation ROC-AUC as tie-breakers.
6. Applies deterministic candidate/variant ordering when validation metrics tie.

The threshold is saved with candidate metadata and reused for test evaluation and inference. A threshold of `0.5` is **not** assumed optimal for F1. Average precision is a precision–recall summary, not exactly the trapezoidal area under the PR curve.

**The held-out test set is not a model-selection or threshold-selection resource.** Full mode evaluates a selected winner per variant on test data, but the overall preferred variant is selected using validation metrics only.

### 6.4 MLflow experiment tracking and comparison

MLflow uses a local SQLite backend (`mlflow.db`) with artifacts in `mlartifacts/` by default. Each candidate run records its model family, variant, mode, hyperparameters, metrics, selected threshold, `training_execution_id`, candidate order, data fingerprints, and the SHA-256 of the YAML configuration. Model logging and standalone joblib packaging are separate outputs.

The comparison script queries `mlflow.search_runs()`, excludes unrelated records, and ranks eligible candidates by the same validation-based policy used by training. With no execution-ID filter, a comparison can include runs from **multiple historical executions** in the local tracking store.

```bash
# Compare eligible completed full-mode runs in local MLflow history.
python -m scripts.compare_experiments

# Inspect quick-mode history or all eligible runs.
python -m scripts.compare_experiments --mode quick
python -m scripts.compare_experiments --mode all

# Isolate one full execution and export its leaderboard.
python -m scripts.compare_experiments --mode full \
  --execution-id <FULL_EXECUTION_ID> \
  --output reports/mlflow_comparison.csv
```

In full orchestration, `scripts/run_pipeline.py` identifies the newly created execution directory, validates its `training_summary.json`, and invokes the comparison with `--execution-id`. **The manual GitHub Actions workflow does not invoke the comparison a second time.** The report is uploaded as a workflow artifact when generated.

For the MLflow UI, run `python -m src.models.train --show-mlflow-command`, execute the printed command, and open the reported local address. Local SQLite history is not automatically included in a fresh Git clone.

### 6.5 Isolated model artifacts and provenance

Full training writes an isolated directory under `models/runs/<execution_id>/`, typically containing:

```text
models/runs/<execution_id>/
    sweep_leaderboard.csv
    training_summary.json
    best_model_pipeline.joblib
    best_model_metadata.json
    baseline/
    robust/
    interactions/
```

The best candidate's deployable pipeline combines its fitted feature preprocessing, a compatibility adapter, and the classifier. The metadata and execution summary record identifiers and fingerprints such as the execution ID, MLflow run ID, source Git revision when available, variant, model configuration, input/preprocessor/model hashes, decision threshold, and YAML configuration hash (in the training summary and MLflow records).

Quick mode stores diagnostic summaries and a leaderboard but **does not** produce the full-mode promotable files. All newly trained candidates remain separate from `models/reference/` until explicit promotion.

## 7. Candidate validation and model promotion

Training, candidate validation, reference promotion, and publishing are separate responsibilities. This prevents a new run from silently replacing the approved model used by robustness evaluation.

### 7.1 Validate without replacing the reference

```bash
python -m src.models.promote --run-id <FULL_EXECUTION_ID>
```

Without `--confirm`, validation checks the source execution's identifier and completion status, candidate/metadata presence, consistency with the selected variant, provenance and recorded model fingerprint, decision threshold, and prediction compatibility. Validation checks saved execution and MLflow metadata; it does **not** retrain the candidate or independently re-measure its performance.

### 7.2 Promote explicitly

```bash
# Run only after reviewing and approving this candidate.
python -m src.models.promote --run-id <FULL_EXECUTION_ID> --confirm
```

The module validates the candidate, backs up the previous reference, verifies the candidate's hash, and replaces `models/reference/best_model_pipeline.joblib` and `models/reference/best_model_metadata.json`. It records metadata including the source execution, promotion time, and explicit promotion type.

The implementation attempts rollback on handled errors. Because the two output files are replaced separately, the operation is **not a single atomic transaction** under arbitrary process interruption. Loading joblib files also requires trusting the artifact source.

### 7.3 Publish an approved reference with DVC

Local promotion **does not** upload model data to S3 or commit a new pointer to Git. An authorized maintainer can publish it explicitly:

```bash
dvc add models/reference
dvc push
git add models/reference.dvc
git commit -m "feat: update promoted reference model"
git push origin main
```

DVC tracks the model and metadata as a directory-level reference. Publishing requires S3 write credentials; anonymous read access is not permission to upload. Reviewers can validate and locally promote their own results without writing to the owner's S3 bucket.

## 8. Git and DVC artifact versioning

The project uses **Git** for code, tests, YAML, README, workflows, and `.dvc` pointers; **DVC + public-read S3** for the raw dataset and approved reference model. `scripts/run_pipeline.py`, not `dvc.yaml`, orchestrates execution.

```bash
# Inspect the current checkout.
git status
dvc status
dvc remote list

# Retrieve the tracked raw data and reference model.
dvc pull data/raw.dvc models/reference.dvc

# To recover a specific version, check out its Git revision first.
git checkout <COMMIT_OR_TAG>
dvc pull data/raw.dvc models/reference.dvc
```

| Artifact | Storage policy |
|---|---|
| Python source, workflows, tests, YAML, README, `.dvc` pointers | Git |
| Raw Adult inputs | DVC + S3 |
| Promoted `models/reference/` model and metadata | DVC + S3, pointer in Git |
| Processed partitions and preprocessors | Generated by preprocessing; not automatically versioned |
| `models/runs/<execution_id>/` | Generated isolated candidates; not automatically promoted |
| `mlflow.db` and `mlartifacts/` | Local experiment history; not distributed with a clone |
| Drift, robustness, and MLflow comparison reports | Generated locally; selected outputs uploaded as GitHub Actions artifacts |

The DVC remote allows anonymous downloads of the configured public-read objects; uploads require credentials. Recovery of old revisions also depends on the matching S3 objects remaining available. Public-read access does not guarantee that requests or transfers are free of S3 costs.

## 9. Data drift monitoring

`src/data/drift_generator.py` creates labeled **control, mild, moderate, and severe** stress-test scenarios. These are deliberate feature modifications, not production observations. `src/data/monitoring.py` compares current feature distributions with the control using Evidently and records which features, if any, drifted.

### 9.1 Detection method and policy

Monitoring uses Evidently's `DataDriftPreset` over the **14 original Adult predictors**, with explicit numerical/categorical feature typing and **Jensen–Shannon distance** (`jensenshannon`). Under the current configuration, a feature's score exceeding `0.10` is treated as drifted.

Evidently outputs an aggregate `DriftedColumnsCount` metric and per-column `ValueDrift` metrics. The monitoring extractor reads the latter to obtain individual feature names, compares each score against its configured threshold, and **verifies that the number of flagged features matches the aggregate count**. Inconsistent or incomplete metrics are treated as errors, not silently interpreted as zero drift.

The project maps the proportion of drifted columns to an operational severity level:

| Drifted-feature share | Status |
|---|---|
| `<= 20%` | `NORMAL` |
| `> 20%` and `< 35%` | `WARNING` |
| `>= 35%` | `CRITICAL` |

These percentages are **project alert thresholds**, separate from Evidently's per-feature statistical threshold and preset-level drift settings.

### 9.2 Run monitoring and inspect outputs

```bash
# First generate stress-test datasets, if they do not exist.
python -m src.data.drift_generator
python -m src.data.monitoring
```

Outputs under `reports/drift/` include each scenario's `_drift.html` visualization, `_drift.json` Evidently snapshot, and combined `drift_summary.json`.

The terminal summary and combined JSON include, per scenario, the drifted feature count, share, severity, and a **`drifted_feature_names` list**. The feature list comes from actual Evidently results, not simply from the generator's list of intentionally modified columns. An unchanged or weakly modified feature may remain below the drift detection threshold.

The command's exit codes are `0` (no critical drift), `1` (critical drift detected), and `2` (execution error). The orchestrator intentionally allows `0` and `1` for synthetic monitoring so robustness evaluation still runs; it does not suppress actual execution errors.

### 9.3 How to interpret results

Distribution drift is **not**, by itself, proof of predictive deterioration. Compare it with labeled robustness metrics in Section 10. In a real deployment, a WARNING would prompt investigation of upstream data quality and persistence of the shift, while CRITICAL would call for urgent investigation and evaluation of model performance. Neither alert justifies blindly retraining or replacing an approved model. This project never automatically retrains or promotes in response to synthetic drift.

## 10. Robustness evaluation under drift

`src/models/robustness.py` loads the **existing DVC-promoted reference model** and its saved classification threshold, predicts on labeled control and synthetic drifted datasets, and compares performance against the control. It does **not** evaluate the new, unpromoted candidate generated during the same run.

```bash
# Use the default generated scenario locations.
python -m src.models.robustness
```

The CLI also supports explicit scenario feature/target paths, for example:

```bash
python -m src.models.robustness \
  --control data/drift/control/X_test.csv \
  --control-target data/drift/control/y_test.csv \
  --mild data/drift/mild/X_test.csv \
  --mild-target data/drift/mild/y_test.csv \
  --moderate data/drift/moderate/X_test.csv \
  --moderate-target data/drift/moderate/y_test.csv \
  --severe data/drift/severe/X_test.csv \
  --severe-target data/drift/severe/y_test.csv
```

The evaluation calculates F1, precision, recall, accuracy, balanced accuracy, ROC-AUC, and average precision where applicable. It produces `reports/robustness/robustness_report.json` and `reports/robustness/robustness_summary.csv`, including differences from the control baseline. **Read current results from those generated outputs**, rather than assuming historical measurements apply to a newly promoted reference or revised drift generator.

## 11. Testing, CI, and orchestration

### 11.1 Automated testing

The suite covers data loading and validation, duplicate preservation and partitioning, preprocessing transformations, training configuration and candidate enumeration, MLflow tagging and comparison, artifact validation/promotion, drift generation, monitoring, robustness, and CLI behavior. Some validation tests intentionally use the actual DVC Adult dataset; others use deterministic synthetic fixtures.

Monitoring tests specifically verify extraction of **individual Evidently-drifted feature names**, agreement between per-column decisions and the aggregate count, JSON/report generation, and CLI statuses.

```bash
# Restore real data before running the complete suite.
dvc pull data/raw.dvc
python -m pytest tests/ -q

# Focused suites.
python -m pytest tests/test_monitoring.py -v
python -m pytest tests/test_train.py -v
python -m pytest tests/test_compare_experiments.py -v
python -m pytest tests/test_data_validation.py -v
python -m pytest tests/test_model_validation.py -v
```

Test totals and dependency warnings change as tests and packages evolve. Inspect the current pytest output and GitHub Actions logs for the result of a specific revision.

### 11.2 Automatic GitHub Actions CI

`.github/workflows/ci.yml` runs on configured pushes and pull requests to `main` and supports manual dispatch. Its two dependent jobs are:

1. **`test`**: Install dependencies, retrieve DVC-managed raw data, run the full pytest suite; failures block the next job.
2. **`train`** (`needs: test`): Retrieve raw data on the separate runner, preprocess, perform **quick-mode** candidate training, and check the minimum validation-F1 gate (currently `0.65`).

This is a test/integration safeguard, **not** full model selection, a deployment pipeline, or automatic reference promotion. The gate should read metrics produced by the intended training execution; reusing shared MLflow stores would benefit from explicit execution-ID filtering.

### 11.3 Shared Python orchestrator

`scripts/run_pipeline.py` provides one stage sequence for local and GitHub Actions execution:

1. Optionally restore DVC inputs (`--pull-dvc`); verify the reference files.
2. Run the complete pytest suite.
3. Preprocess all configured variants.
4. Run quick or full model training.
5. **Full only:** identify the newly completed execution and compare its MLflow candidates by execution ID, exporting `reports/mlflow_comparison.csv`.
6. Generate labeled drift scenarios.
7. Run Evidently monitoring, accepting exit `1` as an expected CRITICAL synthetic alert.
8. Evaluate the existing reference model's robustness.

Failures in required stages terminate execution; successful runs summarize stage durations and exit codes. The workflow does not auto-promote models or write to the DVC remote.

### 11.4 Manual GitHub Actions orchestration

`.github/workflows/ml_pipeline_orchestration.yml` is manually dispatched with `training_mode: quick` or `full`. It installs dependencies, pulls raw/reference DVC objects, checks the inputs, invokes `scripts/run_pipeline.py`, summarizes the run, and uploads the available artifacts.

**MLflow experiment comparison occurs only inside the shared Python orchestrator.** The GitHub Actions workflow has no second standalone comparison step, and its artifact configuration retains `reports/mlflow_comparison.csv` along with drift/robustness outputs and isolated training artifacts. Uploaded artifacts currently have a 14-day retention period. The full-mode comparison CSV is absent by design from a fresh quick-only run.

## 12. Reproducing and inspecting a run

### 12.1 Local execution

```bash
# Use these from the repository root after dependency installation.
python -m scripts.run_pipeline --quick --pull-dvc
python -m scripts.run_pipeline --full --pull-dvc

# If raw and reference DVC artifacts are already present:
python -m scripts.run_pipeline --quick
python -m scripts.run_pipeline --full
```

The full run trains and compares only the candidates defined by the checked-out YAML, records a unique execution ID, and generates current monitoring and robustness outputs. Quick mode checks the infrastructure without building a promotable candidate. Changes to model grids, dependencies, the input data version, or the approved reference model can change the observed measurements.

### 12.2 GitHub Actions execution

Open the repository's **Actions** tab, select **MLOps Pipeline Orchestration**, click **Run workflow**, and choose `quick` or `full`. The manually dispatched workflow restores DVC inputs, invokes the shared orchestrator, and uploads generated artifacts. The automatic `ci.yml` workflow is a separate push/PR quality gate.

### 12.3 Inspect results from the current execution

| Question | Authoritative generated output |
|---|---|
| Which training candidates were evaluated? | `models/runs/<execution_id>/sweep_leaderboard.csv` |
| Which candidate won and why? | `models/runs/<execution_id>/training_summary.json` |
| What model/threshold was packaged? | `models/runs/<execution_id>/best_model_metadata.json` (full mode) |
| How did the current MLflow candidates rank? | `reports/mlflow_comparison.csv` (full orchestration only) |
| Which features were flagged as drifted? | `reports/drift/drift_summary.json`, `drifted_feature_names` per scenario |
| What were the detailed drift statistics? | `reports/drift/<scenario>_drift.json` / `.html` |
| How did reference-model performance change? | `reports/robustness/robustness_summary.csv` and `_report.json` |
| Did tests and stages succeed? | Terminal output and GitHub Actions logs |

All training execution IDs are generated for each run. **Do not confuse an isolated candidate with the DVC-promoted reference model** used by the robustness stage. `reports/mlflow_comparison.csv` represents the currently compared full execution, not a permanent global leaderboard. The local MLflow SQLite store can contain older candidates; always use execution-ID filtering for a run-specific comparison.

### 12.4 Optional model approval

Inspect the candidate and its metrics, validate with `python -m src.models.promote --run-id <FULL_EXECUTION_ID>`, then use the `--confirm` flag **only if explicitly approving replacement**. Publishing the new reference requires separate DVC and Git commands in Section 7. Neither action is part of the automated workflows.

## 14. Scope and limitations

The implementation demonstrates an end-to-end **educational** MLOps lifecycle: controlled data preparation, multiple model families, configurable training, validation-based candidate selection, MLflow history, explicit model promotion, versioned reference artifacts, Evidently monitoring, labeled robustness tests, pytest, and CI/orchestration.

It has the following explicit boundaries:

1. **No production serving or automated deployment.** There is no live prediction API, production traffic integration, or automatic retraining/promotion.
2. **Limited model search.** The current YAML covers four sklearn model families; new families or selection metrics require implementation changes. Optuna and cross-validation optimizers are not included.
3. **Synthetic drift only.** Generated scenarios are stress tests, not production observations; monitoring alerts alone do not establish degraded predictive performance.
4. **Local experiment history.** MLflow SQLite records and training candidates are not included automatically with Git/DVC clones, though the workflows upload selected artifacts.
5. **Versioned reference approval.** Promotion is explicit and local until authorized Git/DVC publishing. The model and metadata update is not fully transactionally atomic.
6. **Statistical and fairness limitations.** The Adult Income dataset is historical, observational, and contains sensitive demographic attributes. The pipeline has not established fairness, external validity, or suitability for consequential individual decisions.
7. **Reproducibility boundaries.** Fixed seeds, pinned packages, DVC pointer hashes, configuration fingerprints, and saved metadata help trace runs but do not guarantee byte-for-byte identical model artifacts on all platforms.
8. **CI metric provenance.** The automatic CI performance gate should stay tied to metrics from the intended quick-training run; explicit execution filtering would further harden it against shared historical MLflow storage.

**Future work** could include cross-validation with duplicate-aware groups, broader/automated hyperparameter optimization, calibration and fairness analyses, production data validation and alert routing, model-serving infrastructure, and stronger artifact-approval transactions. These are possible improvements, not claims of implemented functionality.
